# 要件定義書: お知らせの一覧

## 1. 目的

運営からのお知らせ (メンテナンスの予定、新機能の案内など) を、利用者がアプリケーションの画面で確認できるようにする。利用者がアプリケーションを開いたときに最新のお知らせに気づけるようにし、運営がアプリケーションの外 (メールや SNS) に頼らずに案内を届けられるようにする。

## 2. 範囲

### 2.1 この機能で扱うこと

- 公開されているお知らせの一覧の表示
- 公開日時が未来のお知らせを、その日時になるまで表示しないこと (予約しての公開)

### 2.2 この機能で扱わないこと

- 画面からのお知らせの登録、変更、削除 (当面は、運営がデータベースに直接登録する)
- お知らせ 1 件ごとの詳細の画面
- 既読と未読の管理
- 通知 (プッシュ通知やメールなど)
- 利用者ごとに表示するお知らせを変えること
- 一覧の検索や絞り込み

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| 利用者 | アプリケーションを使う人。ログインしているかどうかは問わない |
| 運営 | アプリケーションを提供し、お知らせを登録する人 |
| お知らせ | 運営から利用者への案内。タイトル、本文、公開日時を持つ |
| 公開日時 | お知らせを利用者に見せ始める日時 |
| 公開中のお知らせ | 公開日時が現在の日時以前のお知らせ |

## 4. 機能要件

### 4.1 一覧の表示

- FR-1: 利用者は、お知らせの一覧の画面を開ける。ログインしていなくても開ける
- FR-2: 一覧には、公開中のお知らせだけを表示する。公開日時が未来のお知らせは、その日時を過ぎるまで表示しない
- FR-3: 一覧は、公開日時の新しい順に並べる。公開日時が同じお知らせは、後に登録したものを先に並べる
- FR-4: 一覧には、公開中のお知らせのうち、新しいものから最大 20 件を表示する
- FR-5: 一覧の各お知らせには、タイトル、本文、公開日を表示する
- FR-6: 本文の改行は、表示にも改行として反映する
- FR-7: 公開中のお知らせが 1 件も無い場合は、お知らせが無いことを表示する
- FR-8: お知らせを取得できなかった場合 (サーバーの障害など) は、一覧を表示できなかったことを利用者に知らせる

### 4.2 画面への移動

- FR-9: 利用者は、アプリケーションの共通のナビゲーションから、お知らせの一覧の画面へ移動できる

## 5. お知らせの内容の条件

運営がデータベースに登録するお知らせは、次の条件を満たすものとする。

| 項目 | 条件 |
| --- | --- |
| タイトル | 1 文字以上 100 文字以内 |
| 本文 | 1 文字以上 2,000 文字以内。改行を含めてよい |
| 公開日時 | 必須。日時はタイムゾーンを含めて扱う |

## 6. 非機能要件

### 6.1 セキュリティ

- NFR-1: タイトルや本文に HTML やスクリプトが含まれていても、解釈や実行はせず、文字としてそのまま表示する
- NFR-2: 公開日時が未来のお知らせは、画面だけでなく、画面が使う通信の応答にも含めない

### 6.2 性能

- NFR-3: お知らせが 1,000 件登録されている状態で、一覧の取得は 95% が 1 秒以内に完了する

### 6.3 運用

- NFR-4: 運営がお知らせをデータベースに登録する手順を、開発者向けの文書に書く

## 7. 前提

- 利用者は、ブラウザーでアプリケーションを使う
- 公開日は、日本時間 (Asia/Tokyo) の年月日で表示する
- この機能は、ユーザーの認証機能 (#1) に依存しない。認証機能が完成していなくても使える
